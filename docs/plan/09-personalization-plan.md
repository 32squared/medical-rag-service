## 0. 한 줄 결론

개인 데이터 해석은 **의료법상 가장 진단에 근접한 위험**(07 §2)이자 동시에 B2B2C 경쟁의 최대 차별점이다. 안전과 합법을 동시에 잡는 유일한 구조는 **"경계선 설계"** — *결정적 규칙엔진이 원시값을 로컬에서 라벨(안정/주의/경고)로 해석하고, LLM·국외(OpenAI)로는 비식별 findings `[R#]`만 넘긴다.* 이 한 원칙이 ① 원시값 유출 ② 국외이전 동의 부담 ③ 역치 환각, 세 문제를 동시에 해소한다. 이미 `vital_input.py:11`·`vital_reference_ranges`(마이그레이션 010)에 이 설계의 씨앗이 있다. 본 문서는 이를 6개 소스로 일반화한다.

## 2. 중심 설계 원칙 — "경계선(boundary)"

```
[디바이스/PHR/OCR]                  로컬(국내·결정적)                          국외/LLM
 원시값(122/78, 96%, 72kg) ──▶ ① 정규화 ─▶ ② 규칙엔진(vital_rules) ─▶ findings[R#] ─▶ ③ RAG 프롬프트
                                  │            (참조테이블 lookup)        (라벨·추세만)
                                  └ provenance/freshness/consent 메타          예) "혈압: 주의 구간 [R1], 최근 점진 상승 [R2]"
```

**불변식**: 원시 수치·정상/비정상 단정은 ③ 경계선을 **절대 넘지 않는다.** LLM은 라벨·추세·인용만 받는다.

이 원칙이 푸는 것:
1. **원시값 유출 0** — 출력에도, 국외 전송에도 122/78 같은 값이 없다.
2. **국외이전 동의 부담↓** — 식별성 높은 원시 바이탈이 OpenAI로 안 감. (단, 라벨도 개인정보일 수 있어 동의는 여전히 필요 → §9)
3. **역치 환각 방어** — LLM이 "정상은 120 미만" 같은 기준을 *생성*하지 않음. 기준은 `vital_reference_ranges`가 소유(`seed_reference_ranges.py:11`의 설계 의도와 일치).

## 3. 법적·윤리 프레임 (08에서 상속)

개인 데이터 해석에 [08](08-competitor-prompt-extraction.md)의 규율을 그대로 적용한다:

- **Population-level test**: "이 해석이 *같은 수치를 가진 누구에게나* 참인가?" → 개인 맞춤 진단 단정 금지. 라벨·일반 메커니즘만.
- **Ceiling**: 측정값 해석은 "어떤 검사·판단이 필요한지는 의료진이 결정합니다" 천장을 넘지 않음.
- **3대 추가 위험축(개인화 고유)**:
  1. **민감정보(개인정보보호법 §23)** — PHR의 정신건강·암·감염병(C형간염·결핵)은 *민감정보*로 별도·명시 동의 + 최소노출.
  2. **국외이전(§28-8)** — 가명정보도 개인정보. LLM(OpenAI) 전송 = 국외이전 별도 동의. → §2 경계선으로 전송량 최소화 + 비개인화 폴백.
  3. **거짓 안심(false reassurance)** — 개인화의 가장 치명적 안전사고. "당신 수치 괜찮습니다"는 진단이자, 틀리면 실해(失害). → 절대 단정 금지, 조건부·인구집단 표현만.

## 4. 데이터 소스 분류 — 6종 + OCR

OCR은 **신호 종류가 아니라 입력 양식(modality)** 이다 — 처방전·검사지·약봉투 사진을 구조화해 *PHR/검사 레코드 저장소로 흘려보낸다.* 별도 신호로 취급하지 않는다.

| 소스 | 신뢰등급 | 주기 | 스키마 | 동의 클래스 | 핵심 함정 |
|---|---|---|---|---|---|
| **혈압기** | 의료근접(가정용) | 점(point) 측정 | 수치 시계열(SBP/DBP/맥박) | 일반 | 가정혈압 기준(135/85) ≠ 진료실(140/90); **1회 측정 판단 금지** |
| **체중계** | 소비자 | 일~주 단위 | 수치(체중/BMI/체지방/근육/내장지방) | 일반 | 체지방·근육은 임피던스 추정치(오차 큼); 느린 변화 |
| **워치** | **웰니스 등급** | 연속 스트림 | HR/HRV/수면/활동/SpO2/ECG | 일반 | **의료기기 아님** — 임상 참조범위 적용 시 거짓경보·거짓안심 양방향 |
| **Vital Sign 기기** | 기기별 상이 | 스팟 다항목 | bpm/spo2/bps/bpd/fever/stress | 일반 | 경쟁사 NAMUH X 모델과 동형; `vital_input.py` 계약 존재 |
| **PHR(공단/심평원)** | 공식 | 일회성/갱신 | 검진·질병·가족력·생활·암검진·처방·진료 | **민감 포함** | 정신건강·암·감염병 민감; 처방=과거이력(현재복용 아님) |
| **OCR(modality)** | **추출신뢰 가변** | 업로드 시 | 비정형→구조화 | 원천 따름 | **추출오류→틀린 라벨→거짓안심.** 사용자 확인 게이트 필수 |

**신뢰 위계(충돌·활성화 정책)**:
`의료근접 디바이스 > 공식 PHR > OCR(사용자 확인 후) > 워치(웰니스 등급) > 사용자 타이핑(개인화 미활성)`

→ 경쟁사 규칙 채택: **사용자가 채팅에 직접 친 수치("내 혈압 150이야")는 개인화 경로를 활성화하지 않는다.** 디바이스/연동 데이터만 활성화. OCR은 *확인 단계*를 거쳐 디바이스급으로 승격.

## 5. 통합 데이터 모델 (canonical personal health store)

두 저장소로 분리한다(성질이 다름):

**A. 시계열 저장소** (혈압기·체중계·워치·vital — 측정값)
```
personal_measurement(
  user_id, signal_key,        -- 'sbp','dbp','hr','hrv','spo2','weight','bmi','body_fat','sleep_min','steps','temp','stress'
  value, unit,
  measured_at,                -- 측정 시각(수신 시각 아님)
  device_grade,               -- 'clinical_near' | 'consumer' | 'wellness'  ← 해석 강도 결정
  context,                    -- 'home'|'clinic'|'rest'|'post_exercise'  ← 참조범위 선택
  source_id, ingest_at, confidence
)
```

**B. 에피소드 레코드 저장소** (PHR·OCR — 사건/소견)
```
personal_record(
  user_id, record_type,       -- 'checkup'|'diagnosis_hx'|'family_hx'|'prescription'|'lab'|'screening'
  payload(json),              -- 구조화 소견(약물=계열만 정규화, 약물명 별도 보관·비노출)
  observed_at, sensitivity,   -- 'normal'|'sensitive'(정신건강·암·감염병)
  source_id, confidence, user_confirmed(bool)  -- OCR은 confirmed=false 초기값
)
```

**횡단 메타(모든 데이터 필수)**: `provenance`(어느 기기/연동), `freshness`(TTL·측정시각), `confidence`(OCR·임피던스 추정), `consent_scope`(이 데이터의 동의 범위).

## 6. 해석 엔진 `vital_rules` 설계 (경계선의 ②)

**전부 결정적(LLM 비의존).** 입력=정규화 측정값, 출력=findings 리스트(라벨+추세+인용, **원시값 없음**).

### 6.1 밴드 라벨링
`vital_reference_ranges` lookup → **안정 / 주의 / 경고** (정상/비정상 단어 금지, 역치·원시값 비노출).
- **참조범위 선택은 메타가 결정**: `context='home'`이면 가정혈압 기준(135/85), `clinic`이면 진료실(140/90) — `seed_reference_ranges.py:56` 이미 두 기준 보유.
- **device_grade가 강도 조절**: `wellness`(워치 SpO2 등)는 경고 밴드를 곧장 적용하지 않고 "웰니스 기기 측정값은 참고용" 프레이밍 + 의료기기 재측정 권유로 완충.

### 6.2 추세 라벨링 (경쟁사 trend_labels 채택)
안정유지 / 점진개선 / 점진악화 / 불안정반복 / 지속상승 / 지속저하 / 일시변화 — **N회 이상**일 때만. 단일 측정은 추세 라벨 금지 + "1회 측정만으로 판단하지 않습니다 [R#]" 명시(`seed:62` 주석과 일치).

### 6.3 조건부 안전문구 주입 (경쟁사 conditional_safety_guidance)
다음 패턴이면 안전문구 1줄 주입(인구집단 수준, 단정 아님):
- SpO2 경고 / 심장활동 높음·낮음 / 맥박 경고 + 타 항목 1개 이상 주의·경고 / 2개 이상 경고.
- **응급 상호작용**: 극단 경고(예: 가정혈압 반복 180/120↑)는 *인구집단 수준 응급 내비게이션*("이 수치대는 즉시 응급 평가가 권고되는 패턴입니다 [R#]")으로 — **"당신은 고혈압 응급입니다" 단정 금지.** 개인 데이터는 내비게이션 바닥을 **올릴** 수 있을 뿐 진단을 **단정**하지 못함. STEP 3 응급경로와의 충돌은 §8 불변식이 규율.

### 6.4 교차신호 패턴 (개인화의 진짜 가치)
단일 항목 해석을 넘어 조합을 인구집단 수준으로: HR↑+스트레스↑+수면↓ / 체중↑+BMI↑+가정혈압 주의 / HRV↓ 지속. → "함께 살펴보면 좋은 항목"으로 제시(진단 아님).

### 6.5 출처 충돌 조정
워치 HR 95 vs 혈압기 맥박 70 → 신뢰위계(§4) + 최근성으로 우선, 또는 범위로 제시. 임의 평균 금지.

## 7. 개인화 주입 레이어 (경계선의 ③)

`generate_response`(`rag_engine.py`)에 personal_context를 주입. 경쟁사 `phr_mode` 방법론 채택:

1. **관련성 게이트 (필수 — 전부 쏟지 않음)**: 질의 scope(신체계통·약물영역) 추출 → 매칭되는 측정/레코드만 표면화. 매칭 0이면 개인화 생략(무관 데이터 과노출 = 프라이버시·소음).
2. **direct/indirect 브리징**: 사용자가 자기 기록을 직접 언급(direct) 또는 증상 scope가 PHR과 겹침(indirect). indirect 브리징이 대부분 — "최근 혈압이 주의 구간으로 기록돼 있어 함께 살펴보면 좋습니다" (단정 아닌 부드러운 점검 제안).
3. **약물=계열만·과거시제**: "과거 ○○계열 처방 이력이 확인됩니다" — 약물명 금지, 현재복용 단정 금지(사용자 확인 전), 인과 추정 금지.
4. **민감정보 최소노출**: 정신건강·암은 최소·비불안 표현, scope 직접 관련 시에만.
5. **demographics 내용 shaping (08 §5)**: 나이·성별·임신이 있으면 *acknowledge에 그치지 말고* 4개 카드 내용·경고패턴·검토항목을 인구집단 수준으로 실제 조정.
6. **출력 형식**: personal_context는 답변 본문 카드에 녹이거나 별도 "📋 내 기록 참고" 1블록. 원시값·필드키·"PHR 블록" 언급 금지.

**주입 위치**: 비응급 경로에서만(EMERGENCY는 개인화 생략 — 경쟁사 phr_mode와 동일). 멀티턴 컨텍스트와 결합 시 [06] 안전 불변식 준수.

## 8. 안전 불변식 (테스트 게이트 — 구현 선행조건)

| # | 불변식 | 측정 |
|---|---|---|
| I1 | 원시 측정값이 출력·국외전송에 **0건** | 정규식·전송 페이로드 스캔 = 0 |
| I2 | "정상입니다/비정상입니다/괜찮습니다" 단정 **0건** | analyzer 금지표현 확장 |
| I3 | stale 데이터(TTL 초과)는 주입 **생략** | `context_feeds` 패턴 재사용, 측정시각 기준 |
| I4 | 사용자 타이핑 수치는 개인화 **미활성** | 활성화는 디바이스/연동·OCR-confirmed만 |
| I5 | 개인 데이터는 응급 **내비게이션만**, 단정 금지 | 골든셋: 극단값→내비, 비(非)단정 |
| I6 | 민감 PHR은 동의 범위 내·scope 관련 시에만 노출 | consent_scope 체크 |
| I7 | 매 턴 응급 재평가 불변(개인화가 응급을 가리지 않음) | 무상태 재분류 유지(`medical_classifier`) |

→ 07 §9.2처럼 **"검증할 코드가 없으면 테스트도 없다"** → vital_rules 구현과 골든셋을 동시 착수.

## 9. Consent & 국외이전

1. **consent_ledger** 신설: 데이터종류 × 용도(해석·LLM전송) × 국외이전 × 민감정보, 각각 시각·버전 기록(감사 요건).
2. **2단계 동의**: ① 데이터 수집·로컬해석 ② **LLM(국외) 전송** — 분리. ②미동의 시 §2 경계선 덕에 *로컬 라벨 해석까지는 제공*하고 LLM 생성만 비개인화 폴백.
3. **민감정보(정신건강·암·감염병)**: 별도 명시 동의 없으면 personal_record에 저장하되 **노출 차단**.
4. **비개인화 폴백 불변**: 동의 철회·미동의·stale 시 즉시 비개인화 답변으로 degrade(서비스 중단 아님).

## 10. 디바이스 우선순위 시퀀싱 (어느 것부터)

| 순위 | 소스 | 근거 |
|---|---|---|
| **1** | **혈압기** | 07 §6이 이미 "혈압 1종" 지정. 수치 단순·임상 밴드 명확(`seed` 보유)·신호 강함·스키마 단순 → 파이프라인 검증용 최적 첫 슬라이스 |
| 2 | 체중계 | 수치 단순·저긴급·느린변화 → 추세 엔진(6.2) 검증에 안전한 두 번째 |
| 3 | Vital Sign 기기 | `vital_input.py` 계약·경쟁사 모델 존재 → 다항목 밴딩(6.1) 확장 |
| 4 | 워치 | 고가치(연속·수면·HRV)지만 **웰니스 등급 프레이밍·집계·정확도 캐비엇** 선행 필요 |
| 5 | PHR | 가장 풍부하나 **민감정보·강한 동의·관련성 게이트** 성숙 후 |
| 6 | OCR | 추출신뢰·확인 게이트 성숙 후. *별도 신호 아닌* PHR/lab 입력 양식으로 합류 |

**원칙**: "측정 없는 개선 금지"(00 P0). 혈압기 1종으로 §2 경계선 + §6 엔진 + §8 불변식 + §9 동의를 *끝까지 한 번* 관통한 뒤 수평 확장.

## 11. 측정 (개인화 고유 KPI)

07의 KPI(유용성·거절률·안전100%·신선도) 위에 개인화 고유 지표 추가:

- **원시값 유출률 = 0** (I1, 하드 게이트).
- **거짓안심률** — "괜찮다" 단정/실제 위험신호 누락 (안전 1급, 목표 0).
- **개인화 유용성 리프트** — 동일 질의에서 개인화 on/off 유용성 차(07 경쟁 벤치마크 골든셋 위에).
- **동의 커버리지·철회 후 폴백 성공률**.
- **stale 억제 정확도** (I3), **OCR 확인 게이트 통과율·오추출률**.

## 13. 미해결 — 결정 필요 (다음 검토)

1. **디바이스 연동 방식**: 직접 BLE/앱 SDK vs 헬스플랫폼 경유(Apple Health·삼성헬스·Google Fit) vs 파트너앱이 §5 스키마로 push. B2B2C이므로 *파트너앱 push가 유력* — 계약(COMPAT-run-graph) 확장 범위?
2. **PHR 출처**: 공단/심평원 직접(Tilko·인증) vs 파트너앱 보유분 수신. 인증·국외이전 난이도 큰 차이.
3. **워치 정확도 표현 수위**: 경쟁사는 "정확도 언급 금지"이나, 우리는 웰니스 등급 *고지*가 오히려 거짓경보 방어에 유리 — 어디까지 고지?
4. **라벨도 국외이전인가**: "주의 구간" 라벨의 식별성 법무 판단(§9-2 폴백 범위 결정).
5. **OCR 확인 UX**: 추출값을 사용자가 확인·교정하는 인터랙션을 파트너앱이 담당? 우리 응답 내 확인?

→ 1·2가 아키텍처를 가르는 핵심. 다음 세션 우선 결정 대상.
