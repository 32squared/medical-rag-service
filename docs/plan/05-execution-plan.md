## 1. 진단 — 커버리지가 문제가 아니라, 문제가 무엇인지 모르는 것이 문제

이 세션에서 실측으로 확인된 사실:

1. **"나 머리아파" 실험**: 두통은 42증상 안에 *있다*(headache, 신경과, red-flag 체크리스트 완비). 그런데 구어체 입력이 증상키 감지·sparse 검색·규칙 분류기 모두에서 매칭 실패 → 체크리스트·진료과·red-flag 부스트가 전부 미발동. **커버리지 안에 있는 증상조차 도달하지 못했다.**
2. **진료과 데이터(11개 과)는 이미 존재하지만 답변에 배선되어 있지 않다** — 자산이 있는데 안 쓰는 상태.
3. **골든 평가셋이 없다** — "커버리지가 낮다"는 현재 측정이 아니라 느낌이다. 어떤 증상이 실제로 질문되는데 못 받아내는지 데이터가 없다.

산수로 보면: 42→60증상 확장은 이론상 +43%다. 그러나 구어체 입력의 도달 실패율이 높으면 실효 커버리지는 그대로 깎인다. 반대로 **도달률 개선은 기존 42증상 전체에 곱해지고, 이후 추가되는 모든 증상에도 곱해진다.** 게다가 새로 추가한 18개 증상도 같은 매칭 문제를 그대로 물려받는다. → **도달(reach) 수선이 폭(breadth) 확장보다 선행되어야 확장이 의미를 가진다.**

## 2. 비전에서 도출되는 판단 기준 3가지

| 원칙 (출처) | 실행 함의 |
|---|---|
| "근거 없는 의학적 주장 금지"의 엔지니어링 버전 = **측정 없는 개선 금지** (품질계획 P0, 마스터플랜 Phase 0 — 두 번 결론남) | 골든셋이 모든 변경의 전제. 커버리지 확장 여부도 골든셋+갭 데이터로 결정 |
| **"평가가 수집을 견인"** — gap 루프가 이미 시스템 설계 사상 (rag_gap_analysis.py) | 증상 확장은 추측이 아니라 수요 데이터(unmapped 질의 집계)가 정한다. 추측성 확장은 자기 설계 철학 위반 |
| **"1~3인 팀 최대 리스크는 기술이 아니라 범위"** (레드팀 Top 5) | 동시에 한 트랙만. 동결 목록 유지 |

## 3. 우선순위 결정: 측정 → 도달 → 수요기반 확장

```
Sprint 1          Sprint 2            Sprint 3
[측정+퀵윈]   →   [도달률 본수선]  →   [수요기반 확장]
골든셋 250        Kiwi 형태소         gap 데이터가 가리키는
진료과 배선        gap 루프 확장        증상 8~12개 추가
증상키 동의어연결                       멀티턴 설계
```

### Sprint 1 (주 1–2) — "측정 기반 + 이미 있는 자산 배선"
1. **골든 평가셋 v1 (250문항)** — 42증상 × *구어체 변형 포함*("머리아파"류를 의도적으로 절반 이상), 고위험 intent(약물·소아·임신·응급) 오버샘플, 신규 KB(P1~P6) 검증 문항 포함. CI 회귀 게이트 배선. **이게 끝나야 "커버리지가 낮다"가 수치가 된다.**
2. **진료과 배선** (퀵윈, 데이터 이미 존재): 증상키 감지 성공 시 `department`를 검색 컨텍스트/답변에 노출 — "이 증상은 일반적으로 OO과에서 진료합니다" + navigation_kr 문서 연계.
3. **증상키 감지에 동의어 확장 연결** (퀵윈): `detect_symptom_keys()`가 synonym_expander 확장 토큰으로도 체크리스트 키워드를 매칭 → medical_shared 서브모듈 데이터 변경 없이 "머리아파"→headache 도달. (Sprint 2의 형태소 도입 전 임시 가교)

### Sprint 2 (주 3–4) — "도달률 본수선"
4. **Kiwi 형태소 분석기 도입** — sparse 토크나이저·증상키 감지·규칙 분류기 키워드 매칭이 같은 정규화를 공유("머리가 아파요"→머리+아프다→두통). 골든셋 전/후 recall 비교로 채택 결정 (측정 없이 머지 금지).
5. **gap 루프 확장** — `rag_gap_analysis`에 ①unmapped 증상 질의 리포트(=커버리지 확장 수요의 공식 신호) ②컨텍스트 차원(증상/약물/제도) 추가. 골든셋 실패 문항도 같은 큐로 환류.

### Sprint 3 (주 5–6) — "수요기반 커버리지 확장 1차"
6. **증상 확장 8~12개** — Sprint 1·2의 갭 데이터가 가리키는 순서로. 예상 후보(검증 전): 소아 연령 분기(발열·기침·발진의 소아 버전), 산부인과 확대(임신 관련 증상), 치과·외과 계열, 알레르기. **확장 단위 = 증상 1개당 4종 세트**: 체크리스트(+구어체 키워드) + 동의어 그룹 + KB 문서 + 골든셋 문항.
7. **멀티턴 문맥화 설계** 착수 (마스터플랜 Phase 1 항목).

### 병렬 트랙 B (코딩 아님, Sprint과 독립) — 마스터플랜 Phase 0 트랙 A
- 식약처 질의서(범위 대조 표시·레드플래그 문구), 약사법 자문(DUR), 마이헬스웨이 활용기관 요건 조사, 1쪽 경제성 모델. 이건 개발 리소스를 안 먹으므로 기다릴 이유가 없다.

## 4. 하지 않을 일 (동결 유지 — 레드팀 합의)
BGE-M3 전환, 학습형 리랭커, GraphRAG/지식그래프, 멀티리전, IoT 제휴, 모바일 앱, 미국 출시 준비. (각각의 해제 조건은 마스터플랜 §4 참조)

## 5. 결정 규칙 (다음에 또 "뭐 먼저?"가 나올 때)

- **증상 확장 시작 조건**: 골든셋 구어체 문항 도달률 ≥85% 달성 *그리고* gap 리포트에서 해당 증상의 수요 확인. 둘 중 하나라도 없으면 확장은 보류.
- **모든 검색·매칭 변경**: 골든셋 전/후 비교 없이 머지 금지.
- **콘텐츠 추가**: 4종 세트(체크리스트·동의어·KB·골든셋) 미완성이면 "추가됨"으로 세지 않는다 — 도달 불가능한 커버리지는 커버리지가 아니다.
