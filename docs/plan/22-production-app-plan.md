# 22 — 생산급 앱 전환 계획 (마이헬스케어 B2B2C)

> 상태: v0.1 (2026-06-24) · 프로토타입(`/app` 데모 하니스 + RAG + 코칭 엔진)을 **출시 가능한 B2B2C 제품**으로 전환하는 설계·로드맵.
> 전제: 코드가 아니라 **결정·아키텍처·단계**를 정한다. 런치블로커(A 의료법·B 동의시스템·D KB검수)는 [LAUNCH-READINESS](../LAUNCH-READINESS.md)와 연동.

---

## 0. 한 줄 요약

프로토타입은 **두뇌(결정적 안전 엔진·RAG·코칭·referral·facility)는 충분히 검증**됐다. 생산화는 그 두뇌를 **(1) 실제 사용자 계정·동의·PHR 위에 올리고, (2) 데모 하니스(`persona_test_server`)를 진짜 프론트엔드+API로 교체**하는 일이다. 신규 발명보다 **재배치·경화(hardening)**가 핵심.

## 1. 프로토타입에서 재사용 vs 재구축

| 구성 | 현재(프로토타입) | 생산 | 판정 |
|---|---|---|---|
| 안전 해석 엔진 | `vital_rules`·`personal_context`·`*_safety`·`wellness_router`·`coaching_*`·`anticipatory`·`referral` | 그대로(순수·테스트 완비) | ♻️ **재사용** |
| RAG 파이프라인 | `rag_engine.generate_response`(Cloud Run) | 그대로 + 스케일/관측 강화 | ♻️ **재사용** |
| 시설 finder | `kr_facilities`(HIRA/E-Gen 실연동) | 그대로 + 캐시·쿼터 | ♻️ **재사용** |
| 영속/이벤트 | `rag_db`·`analytics_events`(PG) | 그대로 + 스키마 확장 | ♻️ **재사용** |
| **프론트엔드** | `persona_test_server` APP_PAGE(단일 HTML, localStorage) | **재구축** (정식 앱/웹) | 🔨 **교체** |
| **계정·인증** | 없음(페르소나 선택) | 본인인증·세션·파트너 SSO | 🆕 **신규** |
| **동의 시스템** | localStorage 게이트(데모) | 동의원장(ledger)·버전·철회·감사 | 🆕 **신규(블로커 B)** |
| **PHR 연동** | 페르소나 합성 데이터 | 공단검진/파트너/웨어러블 실연동 | 🆕 **신규** |
| 데모 하니스 | `persona_test_server`(공개·합성) | 폐기(내부 QA로만) | 🗑️ |

**핵심 통찰**: 백엔드 로직의 ~70%는 이미 있다. 생산화 비용의 대부분은 **프론트엔드 + 계정/동의/PHR 3종 신규 시스템 + 컴플라이언스**.

## 2. 타깃 아키텍처

```
[파트너 앱 (B2B2C)]            [독립 앱 (B2C 옵션)]
   └ 임베드 SDK(WebView/iframe)    └ 모바일 앱(iOS/Android)
            │                            │
            ▼                            ▼
   ┌─────────────────── API Gateway (BFF) ───────────────────┐
   │  인증·레이트리밋·동의 검증·라우팅                          │
   └───┬───────────┬───────────┬───────────┬──────────────────┘
       ▼           ▼           ▼           ▼
   [RAG 서비스]  [코칭 서비스]  [동의 서비스]  [PHR 서비스]
   generate_     coaching_*·   ledger·버전·   검진/웨어러블
   response      gamification· 철회·감사      수집·비식별화
                 adaptive
       │           │           │           │
       └───────────┴─────┬─────┴───────────┘
                         ▼
              [PostgreSQL(암호화) · 이벤트스토어 · 캐시(Redis)]
                         │
              [내부 LLM(국내 우선) · 임베딩 · KB]
```

**경계 설계 불변(생산에서도 유지)**: 원시 측정값·진단명·원문은 **결정적 로컬 엔진**만 보고, LLM·국외엔 **비식별 밴드 라벨만**(방향2 게이트 G1~G6). PHR 서비스가 비식별화 경계를 담당.

## 3. 기술 스택 결정 (권장 + 대안)

| 레이어 | 권장 | 대안 | 근거 |
|---|---|---|---|
| 모바일 | **React Native**(또는 Flutter) | 네이티브 2벌 | 단일 코드·고령 접근성·웹뷰 임베드 재사용 |
| 임베드 SDK | **웹(React) + postMessage 브리지** | 네이티브 SDK | B2B2C 파트너 앱 내 삽입 |
| BFF/Gateway | **Node(Nest) 또는 Python(FastAPI)** | API Gateway 관리형 | 기존 파이썬 자산과 정합 → FastAPI 유력 |
| 백엔드 서비스 | **Python(현 자산 유지)** | — | 안전 엔진·RAG 재사용 |
| DB | **PostgreSQL**(현) + **Redis** 캐시 | — | 이미 사용·암호화 컬럼 |
| 인증 | **본인인증(PASS/통신사)** + OIDC + 파트너 SSO | 소셜 | 의료 맥락 신원확인 |
| 푸시 | **FCM/APNs** | — | §정보통신망법 동의 연동 |
| 인프라 | **Cloud Run → GKE/관리형**(스케일·VPC) | 현 Cloud Run 유지(소규모) | min-instances·국내 리전 |
| LLM | **국내 호스팅 우선**(방향2 G4 국외이전) | 국외+ack | 의료·민감정보 |

> 결정 필요(§9): RN vs Flutter · BFF 언어 · 임베드 우선 vs 독립앱 우선.

## 5. 신규 핵심 시스템 3종 (생산화의 실체)

### 5.1 계정·인증
- 본인인증(의료 맥락 신원) → 사용자 ID·세션(JWT/세션쿠키)·파트너 SSO(B2B2C).
- 권한·가족계정·디바이스 바인딩.

### 5.2 동의 시스템 (🔴 런치블로커 B)
- **동의원장(consent ledger)**: 항목(개인정보·민감정보·국외이전·위치·푸시) × 버전 × 시각 × 철회.
- 모든 개인화/방향2/PHR/위치/푸시 게이트가 **이 원장을 실시간 조회**(현 게이트 G1~G6·coaching_consent를 ledger 백엔드로 승격).
- 철회 즉시 반영·감사로그·동의서 PDF·다운로드/삭제권(개인정보보호법).

### 5.3 PHR 서비스
- 소스: **공단 건강검진**(검진밴드 011/012)·**파트너 PHR**·**웨어러블**(워치/혈압기/체중계).
- **비식별화 경계**: 원시값 적재→로컬 결정적 엔진(`vital_rules` 등)→밴드 라벨만 하류. 민감 PHR(정신·암·감염)=내부 톤 신호, 표면화 0(doc14 활용표).
- 암호화 저장(`personal_record`+`personal_record_sensitive` 물리분리, mig015 설계).

## 6. 컴플라이언스를 아키텍처에 (A/B/D)

- **A 의료법 27조(변호사 검토)** → 밴드 라벨·코칭·referral의 "의료행위 비해당" 의견 확보 전 **개인화 OFF로 출시 가능**(비개인화 RAG는 정보제공). 아키텍처는 개인화 토글을 동의·법률검토에 종속.
- **B 동의 시스템** → §5.2(필수 선결).
- **D KB 의료검수** → 코칭/RAG KB에 **검수 상태 필드 + 검수 워크플로**(이미 review_queue 존재) 게이트; 미검수 콘텐츠 비노출.
- referral(§5.8): 영리 유인·알선 0 — 중립 공공출처만(현 정책 유지).

## 7. 단계별 로드맵

| Phase | 목표 | 산출 | 선결 |
|---|---|---|---|
| **P0 기반** | BFF + 계정/세션 + 동의원장 MVP | API Gateway·auth·consent ledger | — |
| **P1 비개인화 출시** | RAG 채팅 + 시설 finder + 코칭(밴드 없이) | 정식 앱 1차 | A(법률, 비개인화 한정)·D(KB검수) |
| **P2 PHR·개인화** | 검진/웨어러블 연동 + 방향2(국내LLM) | 선제 홈·맞춤 코칭 | A(개인화 법률)·B(동의 완비)·PHR 연동 |
| **P3 리텐션·확장** | 실푸시·적응 루프·게이미피케이션·파트너 SDK | B2B2C 임베드 | GTM(doc21 G2) |

각 Phase는 **현 안전 엔진을 그대로** 얹고, 데이터 소스/동의/프론트만 실체화.

## 8. 리스크·의존성

- 본인인증·공단 PHR API = 외부 제휴/심사(리드타임 김) → P0에 병행 착수.
- 국내 LLM 호스팅 비용·품질 → 비개인화는 외부 LLM 허용, 개인화만 국내.
- 데모 자산 부채: `persona_test_server` 단일 HTML은 생산 프론트로 **이식 불가**(참조용 사양일 뿐) — 재작성 전제.
- KB 얇음(현 dev) → D 검수 + 콘텐츠 확충 병행.
