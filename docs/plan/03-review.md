# 레드팀 검토 의견서 — 개인화 의료 RAG 계획 (01-architecture.md / 02-service-plan.md)

> 작성: 검토자(레드팀) 역할 에이전트 (2026-06-11)

## 총평

두 문서 모두 "규칙 엔진이 해석하고 LLM은 서술만 한다"는 핵심 원칙과 strangler 전환 전략은 수준급이지만, **가장 중요한 전제 세 가지 — 마이헬스웨이에 실제로 연동할 자격이 있는가, '참조범위 대조'가 정말 진단이 아닌가, 모바일 앱은 누가 언제 만드는가 — 를 검증 없이 참으로 놓고 그 위에 12개월 탑을 쌓았다.** 02의 킬러 시나리오 5개 중 2개는 타인(아동·노부모)의 데이터 처리라서 현재 동의 설계로는 법적으로 성립하지 않고, 시나리오 1의 "병용금기 등재되어 있지 않습니다"는 이 계획 전체에서 가장 위험한 한 문장이다. 팀 규모(1~3인 vs 11명), Phase 0 범위, 골든셋 규모, 진출 리전이 두 문서 간에 서로 다르며, 수익모델·비용추정·사고대응·책임보험은 양쪽 모두 부재하다. 이대로 실행하면 0-3개월 안에 일정이 깨지는 것이 아니라, **규제 사전 확인을 건너뛴 채 만든 기능을 출시 직전에 통째로 버리게 되는 경로**다.

## 치명적 결함 (Must-fix)

**1. 마이헬스웨이 연동 자격이 미검증 — '해자 1'이 허가받지 못한 해자** [02 §1.2 해자1, §5 Phase 3-6 / 01 §1.3①, §6.2]
02는 전문기관(한국보건의료정보원) 중계 구조를 "경쟁자가 못 들어오는 레일"로 자랑하지만, **자기 자신이 그 레일에 올라탈 수 있는지를 한 줄도 검증하지 않았다.** 건강정보 고속도로 활용기관은 신청·심사 대상이고, 2025-03 시행 개정법 체계의 제3자 수신자는 법인 요건·보안 요건(사실상 ISMS-P 수준)·심사 리드타임(수개월~1년)이 따른다. 1~3인 스타트업이 ISMS-P 없이 3-6개월차에 "건강정보 고속도로 API 연동"을 완료한다는 로드맵은 비현실적이다.
→ **수정**: 0-3개월에 코드가 아니라 *자격 조사·신청 착수*를 넣을 것. 요건 미충족 시 폴백(검진결과 PDF 사용자 업로드, 수동 입력)을 정식 플랜 A'로 설계하고, ISMS-P 일정·비용을 로드맵에 명시.

**2. "참조범위 대조 표시 ≠ 진단" 논증이 규제 심사를 못 버틴다** [02 §2 시나리오2·5, §3.2 / 01 §2.2]
"155/95는 대한고혈압학회 '고혈압' 분류 범위에 해당", "110mg/dL은 '공복혈당장애' 범위" — **'고혈압', '공복혈당장애'는 그 자체가 질병 분류명이다.** 개인 측정값을 질병 분류 구간에 매핑해 보여주는 행위를 식약처가 "질병 유무 판단 보조"로 볼 여지는 충분하고, 판단 기준이 '표방하는 사용목적'인 이상 "판정이 아니라 대조"라는 내부 어휘 구분은 외부에서 효력이 없다. 더 심각한 것은 **자기모순**: 01 §2.2는 같은 기능군(레드플래그)을 KR "경계(회색)"로 분류했는데 02 §3.2 표는 "대조 표시"를 KR ✅로 확정했다.
→ **수정**: 출시 전 식약처 민원 질의(서면 회신) 또는 규제 자문 의견서를 *기능 개발의 선행조건*으로 격상. 회신 전까지는 질병 분류명 매핑 대신 "공인 기준치(140/90) 인용 + 수치 병기"의 더 보수적 표현으로 시작.

**3. "DUR에 등재되어 있지 않습니다" = 묵시적 안전 보증 — 계획 전체에서 가장 위험한 문구** [02 §2 시나리오1, §3.2 / 01 §2.2]
DUR은 정부가 고시한 목록일 뿐 포괄적 상호작용 DB가 아니다. 미등재를 표시하는 순간 사용자는 "안전하다"로 읽고, 실제 상호작용으로 피해가 나면 false negative 책임이 회사로 온다 — 02 자신이 금지한 "안심 단정"을 약물 영역에서 범하고 있다. 추가로 **개인 복용약과 결합한 맞춤 약물 안내는 복약지도(약사법상 약사 직무)와의 경계**, 전문의약품 정보의 대중 제공·광고 규제 검토가 빠져 있다.
→ **수정**: '등재 사실 있음'만 표시 가능, '등재 없음'은 출력 금지("이 목록만으로 안전을 판단할 수 없습니다" 고정 문구)로 템플릿 비대칭화. 약사법 전문 자문 1회를 DUR 기능의 게이트로.

**4. 소비자 센서 + "과소경고 금지" 원칙 = 119 안내 폭주 설계** [01 §1.2③, §5.2 / 02 시나리오3]
워치 SpO2는 야간 저관류·움직임·피부톤으로 90% 미만 오측이 일상이고, 가정혈압 1회 측정은 자세·커프 오류로 180을 쉽게 찍는다. "보수적 방향으로만 오류" 원칙을 소비자급 센서에 그대로 적용하면 EMERGENCY→119 안내가 남발되어 알람 피로로 신뢰가 붕괴하고, 임계값을 올리면 과소경고 책임이 생긴다. **재측정 프로토콜, 기기 등급별 규칙 분리, 단발성 vs 지속성 구분, 사용자 확인 단계**가 전부 미설계다.
→ **수정**: 레드플래그 v1 스펙에 "EMERGENCY는 (a) 의료기기 인증 기기 출처 또는 (b) 재측정 확인 후"라는 2단계 확인을 명문화하고, false alarm rate를 골든셋과 동급의 출시 게이트 지표로 추가.

**5. 킬러 시나리오 5개 중 2개가 타인 데이터 — 보호자·아동 동의 체계 전면 부재** [02 §2 시나리오1·3 / 01 §3.4]
만 14세 미만은 법정대리인 동의(개인정보보호법 제22조의2)가 필요하고, 마이헬스웨이의 대리인 조회는 별도 제약이 있으며, 성인 가족의 데이터를 보호자 계정으로 수집하는 것은 본인 동의 없이는 불법이다. **대표 시나리오 40%가 현재 설계로 구현 불가.**
→ **수정**: 0-3개월에 "본인 데이터만, 성인만"으로 범위를 명시적으로 좁히고, 보호자 모드는 법적 설계(대리 동의·계정 모델) 완료 후의 별도 Phase로 분리.

**6. 모바일 앱이라는 최대 공수가 두 문서 모두에서 계상 누락** [01 §6.2 Phase0-2 / 02 §5]
HealthKit/Health Connect 수집은 iOS·Android 네이티브 앱(백그라운드 동기화, 건강권한 UX, 스토어 심사)이 선행조건인데, 리포는 백엔드뿐이고 앱 개발 공수·인력이 없다. 또한 "신뢰헤더 인증"의 ingest API 이식 계획은 서버 간 인증 패턴이라 모바일 클라이언트에 적용 불가 — 사용자 단위 토큰 인증 체계가 통째로 빠져 있다.
→ **수정**: Phase 0은 웹 기반 수동 입력만으로 한정하고 HealthKit/Health Connect는 3-6개월로 이동, 최종 사용자 인증 설계를 Phase 0 항목으로 추가.

**7. "밴딩 = 비식별"이라는 법적 오인** [02 해자5 / 01 §5.1, §5.3]
"40대 여성, 고혈압 진단력, ACE억제제 복용, 수축기 2단계 범위"는 밴딩 후에도 **민감정보(건강정보)이며**, 국외 LLM 전송은 여전히 제23조 별도 동의 + 제28조의8 국외이전 문제다. 감사 로그의 findings + 연령밴드 + 성별 + ATC 계열 + 리전을 결합하면 소규모 사용자 기반에서 재식별도 현실적 위협이다.
→ **수정**: 전 문서에서 '비식별' 용어를 '가명화·최소화'로 교체하고, 국외 LLM 전송 동의를 받지 못한 사용자의 폴백 경험(비개인화 모드)을 제품 스펙으로 명시. 감사 테이블의 findings 보존 기간·접근 통제를 별도 정의.

**8. 미국 진출 논리의 자기 파괴 — 레일이 없는 시장에서 레일 해자를 주장** [02 §1.2, §6 / 01 §1.2⑥]
해자 1(마이데이터 레일)·해자 6(한국어 gap 루프)은 미국에서 둘 다 작동하지 않고, 남는 "PD 콘텐츠 영어 KB + 인용 검증"의 PD 콘텐츠는 누구나 무료 복제 가능하다. **미국의 생체신호 레일(HealthKit/Health Connect)은 Apple과 Google 자신의 소유**다 — OS 레벨 Health+AI가 나오면 DTC 웰니스 앱의 차별화는 소멸한다. 미국 전략 전체가 2026-01-06 FDA 지침 개정이라는 발효 5개월짜리 단일 문서에 베팅되어 있다.
→ **수정**: 미국을 "영어 KB 파일럿"으로 격하하고, 글로벌 2순위를 레일·규제 예측 가능성이 검증된 일본으로 재검토. 미국 진출의 전제조건(빅테크 대비 차별화 가설 검증)을 명문화.

**9. 수익모델·비용추정 전면 부재** [02 §5 팀 구성 / 01 §6 전체]
11명 팀 + 위촉의사 3-5인 + 멀티리전 풀스택 + 관리형 MQTT + 쿼리당 GPT-5 비용 + 연 11억 행 스토리지를 계획하면서 **가격·유닛이코노믹스·자금 조달이 두 문서 합쳐 0줄**이다.
→ **수정**: 쿼리당 원가(LLM+검색+검증), 사용자당 월 스토리지, 리전당 고정비를 1페이지로 추정하고, 과금 가설(B2C 구독 vs B2B2C)을 Phase 0 산출물에 포함.

**10. 사고 대응·책임보험·운영 체계 부재** [두 문서 공통 누락]
"119에 연락하세요"를 출력하는 서비스는 그 자체로 24/7 운영 책임을 진다. adverse event 접수·분류·보고 절차, E&O/생산물 배상책임보험, incident runbook, 유출 통지 절차, 열람·정정·삭제(DSR) 도구, 온콜 체계 — 전부 없다.
→ **수정**: 출시 게이트에 "보험 가입 + AE 절차 문서 + 온콜 정의"를 추가. 이는 B2B 세일즈(해자 4)의 전제조건이기도 하다.

## 중요 보완 (Should-fix)

1. **시계열 볼륨 추정의 양방향 오류** [01 §3.3] — "1만 명 전원 공기질 센서 보유"는 과대(현실 부착률 한 자릿수%), 웨어러블 연속 심박·HRV는 누락되어 과소. 수집 화이트리스트를 먼저 정의할 것. 스냅샷 동기 UPSERT는 다중 소스 동시 배치 시 핫로우 경합 — 비동기 갱신 검토.
2. **동의 캐시 TTL의 철회 지연** [01 §3.4] — 철회는 캐시 무효화 이벤트로 즉시 전파, 철회→파기/분리보관 배치 잡 추가.
3. **집안 센서의 프라이버시 결합 리스크** [02 누락 / 01 부분] — 침실 CO2 야간 패턴은 재실·수면·동거 여부를 드러냄(스토킹·파트너 감시 악용 벡터), 비동의 동거인 데이터 수집 문제. 가구 단위 데이터의 제3자 문제와 보존 최소화 정책 필요.
4. **스트레스/HRV 수집의 최소수집 원칙 충돌** [02 §4.2 / 01 §3.1] — "해석 금지"면서 수집은 함 — PIPA 최소수집 원칙(제16조) 충돌. 용도 정의 전까지 수집 보류.
5. **멀티리전 풀스택의 비용·운영 비현실** [01 §1.2⑥] — 6-12개월 내 두 번째 리전 동결, "단일 리전 + 영어 KB"로 글로벌 가설만 검증.
6. **학회 지침(T2) 제휴 실패 시나리오 부재** [02 §4.1-4.2] — 기준 수치(사실정보)의 출처 표기 인용과 본문 적재를 구분하는 저작권 검토로 플랜 B 확보.
7. **의료기기법 트리거 누락** [01 §2.2] — 센서 제조사 제휴 시 앱이 측정 시스템 구성요소로 묶일 가능성. 제휴 계약 시 역할 경계(표시·기록 vs 분석·경고) 명문화.
8. **모델/프롬프트 변경 관리 절차 부재** — LLM 모델 세대교체·프롬프트 변경 시 안전 회귀를 막는 공식 변경관리(승인·카나리·롤백). IEC 62304적 사고방식의 첫 단추.
9. **콜드스타트 미설계** — 신규 사용자의 Day 1(데이터 0) 경험 설계와 연동 전환율·활성화 KPI 부재.
10. **"응급 게이트 recall 100%" KPI의 허상** — 자기 평가셋 100%는 출시 안전성 보증이 아님. 실트래픽 표본 검수 기반 운영 지표(미탐 신고율, false alarm rate)로 보완.

## 두 문서 간 모순/불일치

1. **팀 규모**: 01 "1~3인 생존 조건" vs 02 "12개월 11명 + 위촉의사 3-5인".
2. **골든셋 규모**: 01 250문항 vs 02 500문항.
3. **Phase 0 범위가 서로 다른 제품**: 01 = 생체신호 ingest + 규칙 엔진, 02 = 공기질 연동 + 참조범위 KB.
4. **02의 Phase 0에 동의 원장·ingest 인프라 없음** — 01의 "법적 선행조건 1번"을 02는 건너뜀.
5. **IoT 경로**: 01 본문 "제조사 API 폴링" vs 다이어그램·02 "MQTT/제휴".
6. **레드플래그/대조 표시의 KR 판정**: 01 "경계(회색)" vs 02 "✅".
7. **두 번째 진출 시장**: 01 "EU 또는 US" vs 02 "US 확정".
8. **같은 기능의 이중 설계**: 01 `vital_rules`(findings) vs 02 `vital_reference_ranges`(lookup) — 통합 스펙 부재.
9. **멀티턴 시점**: 02 0-3개월 설계 vs 01 3-6개월 첫 등장.

## 그럼에도 유지할 가치가 있는 강점

- **P1 원칙(해석은 규칙, 서술은 LLM)과 [E#]/[R#] 분리** — 보기 드문 올바른 아키텍처 직관, SaMD 전환 대비 자산.
- **deny-by-default 관할 플래그 + Intended Use 문서의 리포 버전 관리** — 규제 경계를 코드로 강제하는 발상.
- **strangler 전환·멱등 마이그레이션·운영형 인프라 추가 금지 목록** — 1~3인 현실 감각.
- **라이선스 티어링(PD/KOGL/CC BY만 본문 적재)과 "위험 방향 보수 단정만 허용" 비대칭 원칙.**
- 기존 인용 강제 파이프라인이 실재하는 코드라는 점 — 계획의 토대는 허구가 아니다.

## 수정된 우선순위 제안 — 0-3개월에 정말로 해야 할 일 Top 5

1. **규제 사전 확인 패키지 (코드보다 먼저)**: 식약처 민원 질의/자문 — "질병 분류 범위 대조 표시"와 레드플래그 문구의 웰니스 해당성 서면 확인. 약사법 자문 — DUR 표시 경계. 마이헬스웨이 활용기관 요건·리드타임·ISMS-P 필요 여부 조사 및 신청 착수. **이 결과가 제품 범위를 결정한다 — 역순은 매몰비용 제조기다.**
2. **동의·인증 기반 구축**: `consent_ledger` + 최종 사용자 토큰 인증(신뢰헤더 아님) + "성인 본인 데이터만" 정책 명문화 + 철회 즉시 전파. 미성년·보호자 시나리오는 명시적 보류 선언.
3. **가장 좁은 세로 슬라이스 하나**: 웹 수동 입력 혈압 1종 → 참조범위 카드(보수 문구) → 재측정 프로토콜 포함 레드플래그 v0.1(5규칙 내외) → Evidence Pack [R#] 주입·검증. HealthKit·PHR·IoT·공기질 전부 보류 — 슬라이스 하나로 "개인화가 답변 품질을 실제로 올리는가"를 먼저 증명.
4. **골든셋 250문항 + CI 회귀 + 응급 게이트 평가**: 위촉의사 1인 자문으로 시작. false alarm rate를 recall과 동급 지표로.
5. **1페이지 경제성 모델 + 명시적 동결 목록**: 쿼리당 원가, 스토리지 재추정, 과금 가설. 멀티리전·BGE-M3 전환·미국 출시·B2B·IoT 제휴를 "6개월 내 하지 않을 일"로 박제 — **1~3인 팀의 최대 리스크는 기술이 아니라 범위다.**
