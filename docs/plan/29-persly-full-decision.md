# 29. persly-full 도입 결정 요청 (미결)

작성: 2026-09-10 · 상태: **사용자 결정 대기** · 관련: `answer_style.py`, `docs/persly_style_260910/README.md`

## 무엇이 결정 사항인가

동료 세션의 Persly 역공학안은 두 프로필을 제안한다. 이 중 **하나만 구현했다.**

| | persly-safe (구현·배포됨) | persly-full (미구현) |
|---|---|---|
| 형식 | 두괄식 첫 문장, 굵은 소제목 4슬롯, 되묻기 0, 700~1,000자 | 동일 |
| 해석 범위 | L0~L3 (기록 재현·참고범위 분류·항목별 추세·기록된 권고 재전달) | **L5·L6 추가** |
| 질환 | 상황·기전으로만 ("허리 신경 경로의 자극") | **질환명 가능성 제시** |
| 검사 | "어떤 검사가 필요한지는 의료진이 판단합니다" | **검사명 제시** |
| 약 | "의료진·약사와 상담이 필요합니다" | **약 계열 제시** |
| 진료 시기 | 기간 없이 "지속되거나 악화되면" | **기간으로 지정** |
| 가드레일 | 그대로 적용 | **지시형 검출을 끈다** (정본 5절 6항) |

## 왜 persly-safe만 만들었나

정본 5절 6항은 이렇게 요구한다 — "persly-full 은 검사명·약 계열·진료 시기 문장을
내므로 현재 후처리 가드레일(지시형 문장 검출)에 걸린다. dev 실험에서는 프로필이
persly-full 일 때만 해당 검출을 끄고, persly-safe 는 그대로 둔다."

이건 형식 변경이 아니라 **의료 컴플라이언스 가드레일의 우회 경로를 코드에 만드는 일**이다.
프로필 값 하나로 처방·진단 검출이 통째로 꺼지는 스위치가 생기면, 그 스위치가 dev에만
머문다는 보장은 배포 절차에만 의존한다. 동료 세션도 "30인 베타·운영 노출 금지, 법무 회신 전"을
전제로 달았다. 그래서 코드를 넣지 않고 결정 사항으로 올린다.

`answer_style.resolve()`는 알 수 없는 프로필 값을 `default`로 떨어뜨린다(fail-safe).
지금 `X-Answer-Style: persly-full`을 보내도 조용히 default가 되고, 가드레일은 그대로다.

## 결정해야 할 것

1. **persly-full을 dev 실험용으로라도 만들 것인가?**
   - 만든다면: 가드레일 우회를 프로필이 아니라 **별도 env 킬스위치**로 두고
     (`ANSWER_STYLE_ALLOW_DIRECTIVE`, 기본 off), 운영 서비스에는 그 변수를 절대 두지 않으며,
     해당 응답에 `guardrail_bypassed=true`를 STOP 메타·DB에 남겨 사후 감사 가능하게 한다.
   - 안 만든다면: 정본 5절 6항을 "구현하지 않음"으로 확정하고 역공학안에 회신한다.
2. **법무 회신을 기다릴 것인가, 먼저 dev에서 A/B만 볼 것인가?**
3. persly-full 없이도 답변 만족도가 오르는지는 persly-safe A/B로 먼저 볼 수 있다 —
   형식(두괄식·되묻기 0·4슬롯)의 효과와 직접성(L5·L6)의 효과는 분리 측정이 가능하다.

## 권고

**persly-safe로 A/B를 먼저 돌리고, persly-full은 법무 회신 뒤에 다시 본다.**
"답이 시원하다"는 체감의 상당 부분은 두괄식·되묻기 0·구체적 기간에서 나오며 이건 이미
L0~L3 안에서 구현됐다. 직접성 층까지 열어야 만족도가 오르는지는, 형식만 바꾼 A/B 결과를
보고 판단하는 편이 근거가 있다.
